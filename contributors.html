Method & honesty notes

This page reads itself from GitHub. The numbers below are not maintained by hand. On load the page renders a baked-in snapshot (8 Sep 2026) so it works for anyone, then — if you are signed in on the Tracker, whose GitHub token it borrows from the same browser — it recomputes every row from the live API and replaces the snapshot. Stage dates come from each card's LABELED_EVENT history, hours from whether the PR touched Rust or a migration, credit from the PR author. So a project moving to β or closing to γ shows up here the next time someone opens the page, with nothing committed to this repo. The previous version of this page was a hardcoded list of 17 rows that stopped on 19 Aug; it now finds —.

Hours are estimated per project, not per line. A project that touches only the frontend counts 2.5h; one that touches the Rust backend or a migration counts 11h. That is the whole formula — there is no lines-of-code term. Of the projects here, — reach the backend and — do not. The Diff column is shown for context only and no longer drives the number.

Why line count was dropped. Earlier versions charged a flat 55 lines/hr. Measured against what people actually remember spending, that model was wrong in both directions: Riley wrote 531 effective lines in one project that took about 3h (177 lines/hr), while Morgan wrote 405 lines across four projects that took about 10h (40 lines/hr). Same stack, a 4× difference in rate — lines were measuring typing, not effort. What predicts the number is how many separate projects you carried and whether each reached the backend: understanding the problem, wiring it in, running it on localhost and the PR round trip cost about the same whether the diff is 14 lines or 800.

Points, not hours, are the equity measure. A card scores difficulty × strategic multiplier × ship gate. Difficulty is how many layers of the stack the work crossed (1 layer = 3, 2 layers = 8, 3 layers plus a migration = 13) — deliberately coarse, because a finer scale would imply precision nobody has. The multiplier is read off the card's own labels, so what the business says it values and what the model pays for cannot drift apart. The gate reuses the α/β/γ weights the ONC bars already use, which is what stops anyone banking points on code that was never promoted.

Two things this measure does NOT yet do, and both matter before it settles a share.
  • Points scale with card count, so whoever splits work finely scores more. This is the real gaming surface — not padded diffs, which the gate and the up-front difficulty already neutralise. The fix is to budget points at the track level and let a track's cards divide that budget, so splitting a track in two stops creating value. Until tracks carry budgets, read the split as indicative.
  • The strategic multipliers are nearly inert so far. ONC/MIPS fires on 3 cards and integrations on none, because almost all of that work is still an unbuilt idea. So the weighting is a forward incentive, not a retrospective redistribution — it changes what is worth picking up next, and barely moves anyone's current share. Right now 60% of all points carry no multiplier at all.

This page measures the tracked pool only, which is a small part of the product. Against the whole EMR codebase (portal/ on origin/main, generated files excluded) these five contributors account for roughly 16% — 9.6% counting only lines in files they created, 17.8% counting gross additions. The remaining 82–90% predates the tracker or arrives by upstream squash-sync with no pull request in this repository at all: 88.9% of files here were created by no PR. Any share computed from this page alone therefore over-credits the tracked contributors, and the correction is large, not marginal.

These hours are an UPPER BOUND and are known to be too high. An earlier version of this note claimed the model had passed an independent check, because the tracker's own diff-based formula also averaged about 6h per project. That was the wrong comparison — both are estimates fitted to the same recollections, so their agreement was not evidence. Three measurements since say the number is inflated:
  • Commit clock. Clustering every commit into working sessions (90-minute idle gap, 30-minute lead-in) gives Greg 86h, not 518h, and puts all five contributors at 0.7–1.0h per project.
  • A hard wall-clock ceiling. Greg's entire Claude Code history in this lane over the same window — including the tracker itself, research, and work that never became a PR — is 168–236 active hours. A model claiming 518h of coding alone exceeds the total time available to spend, so it is falsified outright, not merely doubted.
  • The calibration denominator was wrong. The 2.5h / 11h rates were fitted so that Greg's 11 then-visible projects summed to his recollection of ~50h. The same method now finds that 60 of his projects had already qualified by that date, so the rate was fitted to a denominator 5.5× too small — which is almost exactly the factor by which it overshoots the commit clock.
Treat the per-person totals here as relative — who carried how much, which is what the page is for — and not as absolute hours. A recalibration against the commit clock implies roughly 0.5h frontend / 2.2h backend.

The rates do not distinguish contributors, only file types. Worth knowing before reading anyone's total: the spread between people in this model (9.7h per project for Eric against 5.0h for Morgan) comes entirely from how much of their work touched the Rust backend, not from any measured difference in how long they took. On the commit clock all five sit within 0.7–1.0h per project of each other.

Cards are matched to PRs only by links a human wrote on purpose — a Closes #n reference, the card number in the PR title, or the tracker's own “Ready for review — @msdrigg · PR #n” comment. GitHub's cross-reference events were tried and rejected: because the repo's CLAUDE.md asks every PR to run bun test, PR bodies routinely mention the card that fixed the test runner, and a cross-reference sweep credited one card to seventeen PRs across four people. The announcement rule is likewise anchored to that phrase and takes only the first PR named, because pasted session summaries in later comments cite unrelated PR numbers — before that fix, one card was being credited to two people on the strength of a quoted summary.

Attribution is by PR author. Commit authorship was unusable — 77 of 110 commits are recorded as invalid-email-address, mapping to no GitHub account. /pull-pr-code-only rewrites authorship to whoever ran the import, so a synced PR credits the importer; #20 (MFA) was corrected to Scott on that basis.

Scott is excluded. He reviews, promotes and gatekeeps rather than being counted as a build contributor here, so projects whose PRs he opened do not appear.

Every total is a floor, and the pipeline is why. — of — projects have not shipped to γ yet, so they count toward the dotted α line and are still accruing. Median time from α to γ is — days (mean —, longest —), and the horizontal run of anyone's dotted line is that latency, not idle time. Totals are also a floor in a second way: a PR with no card link at all cannot be attributed under a per-project model. Riley has three PRs but only one names its card, so two of his are uncounted; Eric's cargo fmt sweep (#513) has no tracker card and so scores nothing.

Stage lines count “reached this stage or beyond”, not “carries this label”. Labels record what someone clicked, not what the code did — — rows never got a status:beta-version label despite shipping past it. A row counts toward every stage it reached or passed, dated by its own label when there is one and otherwise by the earliest later stage on record, so the three lines always nest. Where a β label is missing the dashed line steps on the production date, which reads as “no recorded time in beta” rather than a measured beta date. Label coverage has improved a lot since this page was first built — — rows now carry a real β label, against 3 of 15 in the first hand-built version.

Three rows are hand-linked and cannot be re-derived. #123, #191 and #218 predate all three linking conventions — their PRs (#132, #190, #217) carry no machine-readable reference to a card. Their attribution is inherited from the first hand-built version of this page and is carried in a small override map so the live rebuild does not drop them. #191 in particular looks doubtful — its card and its PR do not obviously describe the same piece of work — so treat that one as unverified rather than measured.
